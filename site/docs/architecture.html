nektar architecture

nektar is a BSV-native implementation of the Merkle Automaton (arXiv:2506.13246). It is encrypted, provenance-bearing agent memory whose history is append-only and anchored. State transitions are enforced by Rúnar UTXO contracts. Everything a verifier needs ends in the BSV header chain (GEN-003).

9. Instance synchronisation — bstack carriers

mermaid
sequenceDiagram
  participant A as agent A
  participant H1 as host 1 (tm_nektar_* lanes)
  participant H2 as host 2 (tm_nektar_* lanes)
  participant B as agent B
  A->>H1: signed carrier (funding-tree spend, expiry)
  A->>H2: same carrier
  Note over H1,H2: host module admits only proven-tree carriers,<br/>fresh signatures, unexpired artifacts
  B->>H1: read lane
  B->>H2: read lane (parallel, quorum)
  H1 & H2-->>B: envelopes / records
  Note over B: verifies signatures + BEEF/SPV locally —<br/>hosts are relays, never trust roots

Artifacts move as carriers on tm_* lanes admitted by each host's module — wants/offers on tm_nektar_<net>_<lane>, deal envelopes via bbox, identity records via bfinger (tm_finger), journals via blogs (tm_log_*). Knowledge shards transfer as verified packs over /v1/pack/{shard} or importShard — there is no chain-side UTXO sync between hosts; the old GASP overlay sync was removed with the rendezvous transport.

Everything on these lanes is a stock Lightweb encoding; nektar adds no custom envelope or record format:

  • Market artifacts are canonical nkt1 records — a CBOR record

({1: kind, 2: body} plus preserved extension keys) claiming the nkt1 magic, so any stock recordReader walks them. The legacy JSON payload is still accepted on decode, and NEKTAR_MARKET_V1=1 opts back out of v2.

  • Deal envelopes are stock bbox records — BRC-78 sealed, opened by the

counterparty's wallet only. Stock plaintext members carry nektar content (nektar: object) and evidence pointers ride the stock refs[] member ({url, sha256, length} — https/uhrp URLs only, per stock admission).

  • Objects are content-addressed: packs, evidence bundles, and proofs are

written to bstore AND as CHIRP closures (chirp://<identifier>); refs carry both the chirp URI and the keyed {bucket, key, sha256, size}. Readers resolve CHIRP first and verify the closure, then fall back to the keyed ref — every unsigned read is digest-verified either way. The operator's /v1/pack/{shard} origin is a compatibility fallback, not the data plane.

  • Discovery is committed: the operator's bfinger record refs advertises

the nektar-packs store — an RFC-6962 root over member commitments. Each pack is a kind-5 sub-record (its carrier commitment is the member); a kind-6 manifest lists members once count > 1 and refs.head points at it. A reader holding only the operator pubkey resolves the whole store through ls_finger — resolveFinger surfaces the record's decoded refs, and resolveStoreMembers walks {identityKey, carrier: head} (the third stock question class) to the member records — no /.well-known or origin dependency.

Object reads share one resolver (fetchObjectByRef): CHIRP signed → CHIRP unsigned → keyed signed → keyed unsigned. delivered envelopes carry the pack's plaintext refs[]; receipts carry proofStore locators so ZK proof bytes resolve via chirp/<commit> with no origin call. Residual refs gaps: stock refs[] admit https/uhrp only, so a local http gateway can't ride an envelope ref (the message fields still carry everything).

Payments use two stock rails, each where it fits. x402-style tool/quote invoices settle through the stock LedgerReceiver — payments.jsonl (the stock LedgerFile name and line format) in the data dir, claimed atomically: a txid replay AND a conflicting input spend are both refused. Deal payments keep the NektarAnchor sale escrow covenant: it is the application primitive (timeout refund, disclosure binding) that no stock rail replaces, so envelope Payment/checkPayment is not bolted on as a parallel stream. PaymentGate/ decidePayment/LedgerReceiver-as-envelope-payee stay unadopted — they gate a stock host engine's paid question classes, and nektar runs no stock host; LookupFront stays unadopted for the same reason (client, not front operator). keyed is Go-only at the vendored upstream versions with no TS twin, so fragment keys remain the local HKDF scheme (divergence recorded in the plan).

Residual central dependencies are infrastructure, not application servers: the broadcaster, a WoC/chaintracks tip source, the regtest node, and the deployment's S3/bstore gateway — all replaceable, none trusted with content or settlement truth.

ADR-020 — hash-based STARK over the anchored SHA-256 tree

Context. Wright §13 / App. C define π = ZKMerkleProve(h_j, R_n, P_j) over the tree anchored on-chain. H is "a collision-resistant hash, e.g., SHA-256". Proofs are non-interactive via Fiat–Shamir. Only "public parameters for H, ZKProve, ZKAccess" are needed, with no central authority. ADR-015 departed from this in two ways:

  • a second (Poseidon) tree, whose equality with R_n was never proven;
  • a Groth16 trusted setup.

Options evaluated (measured or documented, Nov 2026).

OptionFinding
SP1 (Plonky3 STARK) — the BSV-stack choice (Rúnar ships an SP1 FRI verifier; BSVM verifies SP1 STARKs on-chain)Rejected: Succinct's security model states "individual STARK proofs in SP1 do not currently satisfy the zero-knowledge property". Only the Groth16/PLONK wrapper is ZK, which reintroduces a trusted setup. A non-ZK proof would leak the leaf, breaking §13.
RISC Zero succinct receiptChosen: documented as a zero-knowledge STARK (DEEP-ALI + FRI, trace noise added; "hides all program inputs"). Composite receipts leak the trace length, so only succinct receipts are accepted.
Noir/UltraHonkNot chosen: universal setup (KZG), so not hash-only.
Bulletproofs over SHA-256Transparent, but impractical prover cost at depth 16.

Measured on this machine (CPU only, prover in Docker; spike tools/stark/):

  • Program: reproduces core/merkle.ts for all 561 leaf positions of sizes 1..33, and refuses index ≥ size, a short path, a broken odd self-pair and a foreign leaf at the odd position.
  • Real Teranode anchor 662e9ae9…7a77:
  • prove 34.9 s, succinct receipt 224 KB;
  • WASM verify in native Node 37–83 ms;
  • the proven root equals the anchored R and the size equals the anchored size.
  • WASM verifier rejects: a tampered receipt, a swapped header root or queryId, and a foreign program ID.

On-chain verification: not available for RISC Zero receipts in Rúnar, which only has an SP1 FRI verifier. Verification stays off-chain against the SPV-verified anchor, which §13 permits ("executable on-chain if necessary").

Consequences:

  • the Poseidon tree, the Groth16 circuits and ceremony, and the anchor's poseidonRoot are removed (NektarAnchor v3, fresh regtest chains);
  • the nullifier is replaced by a verifier-issued single-use queryId;
  • proofs are larger (224 KB vs 389 B, all off-chain);
  • proving is slower (≈35–50 s per proof on CPU);
  • trust moves from a ceremony to the RISC Zero implementation plus the pinned program ID.

ADR-021 — one repair substrate for every fan-out leg

Context. Three delivery semantics had accreted for the same host set: publishArtifact/sendBox produced per-host repair rows through trackFanout, publishFinger reconciled on its own schedule, and numbered appendLog/anchorLog/publishMinedLog batches produced none — a host that missed batch N kept a permanent replica gap that reader-side fanout masked but nothing repaired.

Decision. Every multi-host submission reports its per-leg outcome ({ ok, missed }) and the caller queues a repair row keyed on the journaled carrier (log:{stream}:{seq}, logpub:{stream}:{txid}, finger:sub:{kind}:{id}). The journal stays the retry layer; sends keep retryWaits: [] so a dead host never sleeps the message path.

Consequences. Missed hosts converge on the same mechanism for every stream type; gap repair is visible in deals {operationId} instead of silent; new fan-outs must return missed — a publish that hides leg outcomes is a lintable smell.

ADR-022 — bstack surface grouped by consumer

Context. bstack/src/index.ts star-exported every module, so wire contracts (market-wire, box, log codecs) were indistinguishable from plane internals (journal, trees, host plumbing) at the boundary — an interop implementer could not tell which exports are the protocol, and knip/depcruise cannot police a star surface.

Decision. The index lists named exports in three groups: the wire contract a counterparty implements, the delivery plane that runs it, and the sandbox-host module an overlay loads. Adding to the first group is a wire-contract decision, not a drive-by export.

Consequences. The public surface is enumerable and reviewable; star exports inside src/ remain banned by convention (new export * in bstack is a review flag).

ADR-023 — memory domain behind a package boundary

Context. @nektar/mcp concentrated three subsystems — the memory domain (memory/ + the *ops modules it wires, ≈5k LOC), the protocol surface (server/http/dispatch), and runtime assembly — carrying ~40% of all churn with the widest fan-out in the repo. The god-file is already gone (memory.ts 1976→315-line facade over a layer chain); the remaining hazard is that the most-changed package is also the widest blast-radius.

Decision. @nektar/memory is the domain boundary — executed. The seam resolved the second way: the ops port interfaces moved with the domain (ports.ts) while the concrete *Ops impls stayed in mcp, wired at the composition root (mcp/src/memory.ts). The subtree's mcp-root imports went to zero, so the extraction moved coupling, not just files.

Consequences. mcp sheds the layer chain (11239→9138 LOC; @nektar/memory enters at 2394) and the memory model is importable without the app tier; check:arch carries the new package's edges and mcp's residual is the composition root plus the concrete *Ops impls, not domain coupling.
